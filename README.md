# Marketplace API

Курсовий проєкт, Robot Dreams **Node.js PRO**. Один сервіс, який я достроюю від
ДЗ#9 до захисту на #34: спека → схема БД → транзакції → черги → auth → деплой.

## 1. Що це за сервіс

Маркетплейс. Продавці виставляють товари, покупці оформлюють замовлення.
Продавцю потрібна вітрина, облік залишку й можливість крутити ціну — акції та
промокоди. Покупцю — каталог, у якому реально знайти потрібне, і оформлення без
сюрпризів у підсумку.

Складне тут не «показати каталог». Складне — порахувати підсумок **один раз і
правильно**, поки навколо все рухається. Залишок міняють інші покупці. Акція
закінчується за годинником. Промокод має спрацювати рівно раз на людину. Мережа
може надіслати той самий запит двічі. Це чотири різні механізми, і всі чотири
сходяться в одну транзакцію оформлення замовлення — саме тому вона й цікава.

Чого люди хочуть від сервісу:

| Роль | Хочу | Щоб |
| --- | --- | --- |
| Покупець | звузити каталог фільтрами (ціна, рейтинг, наявність) і гортати результат сторінками | знайти потрібне серед 10 000 товарів |
| Покупець | оформити одне замовлення на кілька товарів і бути впевненим, що подвійний клік не створив другого | не заплатити двічі |
| Покупець | ввести промокод і бачити в підсумку, звідки взялася кожна скидка | розуміти суму, а не сперечатися про неї |
| Продавець | виставити товар із залишком і фото | його побачили в каталозі й не купили більше, ніж є |
| Продавець | запустити акцію на свій регіон і одразу дізнатися про нове замовлення | продати залишок і відправити того ж дня |

## 2. Домен

Шість доменних сутностей. `OrderItem` я рахую частиною агрегату `Order` — рядок
замовлення сам по собі не існує й не має власного життя. Усі шість стануть
таблицями на #12 і entities на #13.

```
User      ─< Product        продавець володіє товарами
Product   ─< Promotion      автоматична акція: сезонна або за кількістю
User      ─< Order          покупець оформлює замовлення
Order     ─< OrderItem      позиція зі знімком ціни та скидки
OrderItem ─  Product
Order     ─  Promotion      промокод: одна акція на все замовлення
Order     ─  Payment        1:1, незворотна операція
User      ─< PointsEntry    бонусні бали: append-only, баланс = SUM
Order     ─< PointsEntry    нарахування за замовлення і списання в ньому
User      ─< Notification   (інфраструктурний запис, не доменна сутність)
```

| Сутність | Ключові поля | Чому вона в домені |
| --- | --- | --- |
| `User` | `id`, `email`, `password_hash`, `role`, `created_at` | три ролі з різними правами: buyer · seller · admin (#24) |
| `Product` | `id`, `seller_id`, `category`, `title`, `price` `NUMERIC(12,2)`, `stock`, `rating_avg`, `rating_count`, `image_keys[]`, `created_at` | `stock` — те, за що конкурують (#14); фото в S3 (#26); картка товару — гаряче читання (#23) |
| `Promotion` | `id`, `product_id`, `kind`, `code`, `percent_off`, `min_qty`, `region`, `starts_local`/`ends_local` + `timezone`, `starts_at`/`ends_at` `timestamptz` | ціна стає результатом правил на момент оформлення, а не властивістю товару. `kind`: `seasonal` · `quantity_tier` · `promo_code`. `region` — акція для одного регіону; `*_local` + `timezone` це те, що ввів продавець, `*_at` — та сама мить в абсолюті, по ній працюють запити |
| `Order` | `id`, `buyer_id`, `device_id`, `region`, `status`, `subtotal`, `discount`, `total` (усі `NUMERIC(12,2)`), `currency`, `promo_code_id`, `points_spent`, `created_at` | точка входу транзакції (#14). Три суми, а не одна — щоб підсумок був прозорий. `points_spent` окремо від `discount`: бали не змінюють ціну, вони покривають частину суми до сплати — і не більше, ніж сума позицій без акції |
| `OrderItem` (у складі `Order`) | `order_id`, `product_id`, `qty`, `unit_price`, `discount`, `promotion_id` | знімок ціни **і** скидки: ні новий цінник, ні закінчена акція історію не переписують. Із `promotion_id` виводиться й право на бали — акційна позиція їх не дає й не приймає |
| `Payment` | `id`, `order_id`, `amount`, `status`, `provider_ref`, `created_at` | незворотний ефект → outbox + idempotency (#22) |
| `PointsEntry` | `id`, `user_id`, `order_id`, `kind`, `amount` `integer`, `status`, `matures_at`, `created_at` | бонусні бали як **append-only журнал**, а не колонка-баланс: баланс = `SUM`. `kind`: `earned` · `spent`; `status`: `pending` → `available` → `spent`. `matures_at` — коли нарахування дозріває (#19 · #23). База нарахування — позиції замовлення **без** акції |

Поза шісткою, як інфраструктура: `Notification` — запис про доставку сповіщення,
і `outbox` (#22). Обидва це проєкція доменних подій, а не доменний стан, тому в
домен я їх не рахую, хоч таблицями вони й будуть.

Схема цих сутностей — `db/schema.sql`: сім таблиць, десять `FOREIGN KEY`,
інваріанти в `CHECK`, а не в коді (`total = subtotal - discount`, промокод не
має товару, нарахування балів має дату дозрівання). `Product.seller_id` і
`Order.buyer_id` в ній є з першого дня як `NOT NULL`: без власника не працює
ані каталог продавця, ані «мої замовлення за період» (`db/queries/q1.sql`);
#24 лише почне брати значення з токена замість тіла запиту. Категорія товару —
закритий перелік у `CHECK`: `shoes · clothing · electronics · home · sports ·
books`. `Promotion`, `Payment` і `PointsEntry` уже і в схемі, і в сіді — рівно
настільки, щоб кожен FK був перевірений під обсягом; бізнес-логіку на них
навісить #14, ресурсами API вони стануть на #22 і #19.
`rating_avg` — денормалізований агрегат, а не `JOIN` по відгуках, і `NULL`,
поки відгуків нема; сама сутність `Review` зʼявиться, коли буде кому їх писати.

`openapi/openapi.yaml` — це контракт **v1**, знімок на момент ДЗ#9: гроші в
ньому ще `*_cents` цілими копійками, і немає ні `category`, ні `region`, ні
фільтрів каталогу. Дані там лежать у памʼяті, тож `NUMERIC` і decimal-рядки
переїдуть у спеку разом зі схемою БД на #12–#13 — до того їм нема на що
опертися.

### Перевірка домену

| ✔ | Вимога до домену | Де саме в домені | Знадобиться |
| --- | --- | --- | --- |
| ✅ | ≥ 2 ролі з різними правами | `User.role`: buyer · seller · admin | #24 RBAC |
| ✅ | обмежений ресурс, за який конкурують | `Product.stock` — двоє купують останню штуку; промокод — рівно раз на користувача; баланс балів — двоє замовлень на останні 100 | #14 транзакція |
| ✅ | операція з незворотним ефектом | `Payment` — гроші списані | #22 outbox |
| ✅ | подія, про яку треба сповістити | зміна статусу замовлення й дозрівання бонусних балів → `Notification` | #18 · #19 |
| ✅ | сутність із файлами | фото товару, S3-ключі на `Product` | #26 presigned URL |
| ✅ | часто читають, рідко змінюють | картка товару, каталог продавця, список активних акцій | #23 cache-aside |
| ✅ | 4–6 сутностей + важкий запит | шість; підсумок кошика (товари + активні акції + залишок) і каталог із фільтрами — обидва на гарячому шляху | #12 · #13 |

Сім із семи. Половина домену вже описана й провалідована у спеці ДЗ#9.

## 3. Архітектурні рішення

Сервіс — **один довгий Node-процес** на NestJS 11 поверх Express 5. Це не деталь
хостингу, а те, що видно в коді: `IdempotencyService` тримає ключі в памʼяті, і
працює це тільки поки інстанс один. Другий інстанс віддасть те саме замовлення
двічі — тому сховище ключів переїде в Redis на #23, а не «колись, якщо
знадобиться». Serverless не розглядаю з тієї ж причини: між викликами там не
залишається нічого.

| Рішення | Чому | Приїде на |
| --- | --- | --- |
| **Postgres** | потрібні транзакції: двоє купують останню штуку, і eventual consistency тут коштувала б овербукінгом. Підсумок з акціями рахується в тій самій транзакції — інакше акція, що закінчилась посеред оформлення, дасть суму, якої не існувало | #12 · #13 |
| **TypeORM** | міграції як код, entities звірені зі спекою | #13 |
| **RabbitMQ** | сповіщення й e-mail не мають тримати HTTP-відповідь: замовлення оформлене — решта асинхронно | #19 |
| **Outbox** | «гроші списані» не можна ні втратити, ні продублювати: запис у чергу в тій самій транзакції, що й `Payment` | #22 |
| **Redis, cache-aside** | картку товару читають набагато частіше, ніж змінюють. Плюс спільне сховище idempotency-ключів замість памʼяті процесу | #23 |
| **JWT + RBAC по `User.role`** | покупець бачить своє, продавець своє, адмін усе. Поки `security: []` у спеці документує, що авторизації немає **свідомо** | #24 |
| **S3 + presigned URL** | фото товару не мають ходити через Node-процес | #26 |
| **Keyset-пагінація з фільтрами** | фільтри її не ламають — ламає зміна `ORDER BY`, тому курсор носить відпечаток фільтрів і чужий відхиляє як `invalid-cursor`. Фільтри, індекси й SQL — у `docs/design-notes.md` | #12 · #13 |
| **`NUMERIC(12,2)` для грошей** | ціни десяткові (`259.99`), арифметика через `decimal.js`, в API рядок. `float` не використовується ніде: `0.1 + 0.2` дає `0.30000000000000004`, і на кошику з 30 позицій це вже видима копійка. Політика округлення скидок — у `docs/design-notes.md` | #12 · #14 |
| **Бали дозрівають відкладено** | нарахування за замовлення стає доступним через N днів, тож потрібна задача, що спрацює пізніше. Беру періодичний прохід по `(status, matures_at)`, а не відкладене повідомлення: стан живе в Postgres і не залежить від того, чи брокер його не втратив. Задача ідемпотентна через `UPDATE … WHERE status='pending'` | #19 · #23 |
| **Регіональні акції** | регіон — це окремий рядок `Promotion` зі своїм вікном у своїй зоні, тож `ends_at` залишається однією абсолютною миттю, а запит — однією умовою. Ключ кешу отримує `region`: кілька значень, а не 38 таймзон | #12 · #23 |
| **Docker → compose → K8s** | локально compose з Postgres і Redis, далі кластер | #28 |

## 4. Trade-offs — чого свідомо не буде

Формат: не робимо X, бо Y — де Y це ціна альтернативи, а не брак часу.

- **Повернень і refund не буде.** Оплата — фінальний стан замовлення. Якби
  платіж можна було відкотити, «незворотна операція» на #22 стала б звичайним
  CRUD із полем `status`, і outbox не мав би що захищати.
- **Доставки й логістики не буде.** Замовлення закінчується оплатою. Трекінг,
  склади й перевізники — це другий сервіс, і нового механізму він не приносить.
- **Мультивалютності не буде, але ціни справжні десяткові.** Одна валюта,
  `NUMERIC(12,2)` у БД, рядок `"259.99"` в API, `decimal.js` для арифметики.
  `float` не використовую ніде — саме через нього ця тема й існує. Курси валют
  на дату операції нічого не додають ні до транзакцій, ні до черг.
- **Акцій три типи, і на цьому все.** Сезонна, за кількістю, промокод. Бандли й
  безкоштовна доставка від суми — ні: кожне це новий тип правила й нова гілка в
  розрахунку ціни, а сам механізм три наявні вже покривають повністю.
- **Бали — платіжний засіб, а не четвертий тип акції.** Скидка змінює ціну, бали
  покривають частину суми до сплати. Тому вони живуть на замовленні
  (`points_spent`), а не в `Promotion`, і в чеку це окремий рядок «оплачено
  балами», а не мовчазне зменшення ціни товару.
- **На акційний товар бали не діють — ні в нарахування, ні в оплату.** Позиція,
  у якої заповнений `promotion_id`, виключена повністю: за неї не нараховують і
  її не можна покрити балами. Інакше та сама позиція здешевлюється двічі —
  акцією і балами, — і маржа з'їдається там, де її вже віддали. Окремого поля
  для цього не треба: `points_eligible` виводиться з `promotion_id`, тож
  правило не може розʼїхатися з даними. Промокод eligibility **не** знімає — він
  діє на замовлення, а не на товар.
- **Баланс балів — не колонка, а сума журналу.** `User.points_balance` не дав би
  відповісти на «чому в мене 340 балів», а втрачений або подвоєний `UPDATE` не
  можна ні знайти, ні відкотити. Append-only `PointsEntry` коштує `SUM` на
  читанні — і за це віддає повну історію.
- **Бали не згорають.** Термін життя балів вимагав би другої відкладеної задачі й
  списання строго FIFO (найстаріші першими, щоб не пропали) — тобто ще одного
  порядку, який треба тримати в транзакції. Механізм відкладеного нарахування я
  вже отримую з дозрівання; згорання додає роботи, а не розуміння.
- **Один промокод на замовлення, і рахується він після автоматичних акцій.**
  Стек кодів або пріоритети між правилами вимагають рушія правил — і саме там
  живуть баги, через які товар відпускають за копійку.
- **«Один раз на девайс» не гарантую.** `device_id` пишу й ним рейт-лімітую, але
  інваріантом він не є: інкогніто, чистка сховища й новий телефон скидають його
  безкоштовно. Жорстко тримаю тільки те, що тримається індексом — один раз на
  користувача.
- **Акції регіональні, але локальної півночі для кожного покупця не буде.**
  Регіон — окремий рядок акції зі своїм вікном, тож усе лишається однією
  абсолютною миттю й однією умовою в запиті. «До півночі там, де ти» на одному
  рядку розтягнуло б акцію на 26 годин, зламало б `WHERE ends_at > now()` і
  розмножило б ключ кешу на кожну зону замість кількох регіонів.
- **Пошук лише префіксний.** `%nike%` не бере жодного індексу й перетворює
  кожен запит каталогу в seq scan. Повнотекстовий вимагає `pg_trgm` або окремого
  рушія — ще один компонент у compose і ще одна консистентність.
- **Платіжного провайдера емулюю.** Реальний Stripe дав би вебхуки й ретраї, але
  саме їх я і пишу руками на #22. Sandbox замінив би навчання на конфігурування.
- **Монолітний Nest, не мікросервіси.** Черга — для фонових задач, а не щоб
  різати сервіс. Розподілена транзакція між «списати залишок» і «прийняти
  платіж» коштувала б saga-компенсацій; в одному процесі це один `BEGIN`.
- **Eventual consistency тільки у сповіщеннях.** Залишок строго транзакційний:
  пізнє сповіщення користувач не помітить, овербукінг помітить одразу.

## 5. Configuration

Одне речення, з якого росте весь розділ: **зламаний конфіг має вбивати процес на
старті, а секрет — жити в одному місці й змінюватись без деплою.**

### Змінні

Усі змінні описані однією zod-схемою — `src/config/env.schema.ts`. Вона ж
породжує TypeScript-тип `Env`, тому по коду немає жодного читання оточення
напряму: є `ConfigService<Env, true>`, і `get()` повертає готовий тип без
`undefined`.

| Змінна | Значення | Обов'язкова | Джерело | Навіщо |
| --- | --- | --- | --- | --- |
| `NODE_ENV` | `development` \| `test` \| `production` | ні, дефолт `development` | `.env` / оточення | режим роботи |
| `PORT` | число 1–65535 | ні, дефолт `3000` | `.env` / оточення | порт HTTP-сервера |
| `LOG_LEVEL` | `debug` \| `info` \| `warn` \| `error` | ні, дефолт `info` | `.env` / оточення | рівень логування |
| `DB_URL` | `postgres://user@host:port/db` — **без пароля** | **так** | **сховище #11**: `.env` поза git (dev) · оточення від оркестратора (prod) | куди підключатись до Postgres — база `marketplace` з `docker-compose.yml` |
| `DB_PASSWORD_FILE` | шлях | ні, дефолт `./secrets/db_password` | `.env` / оточення | де лежить пароль БД |
| `DB_POOL_MAX` | число 1–100 | ні, дефолт `10` | `.env` / оточення | розмір пулу `pg` |
| `DRIFT` | `0` \| `1` | ні, дефолт `0` | `.env` / оточення | демо дрейфу контракту з ДЗ#9 |
| `SLOW_MS` | число ≥ 0 | ні, дефолт `0` | `.env` / оточення | штучна затримка `POST /orders` (демо 409 з ДЗ#9) |
| — | вміст `secrets/db_password` | так | **файл-секрет** | пароль ролі `app_user` |

Останній рядок — не змінна, і це головне рішення розділу. Пароль БД свідомо
живе поза схемою: чому — нижче, у «Ротації».

«Сховище» для `DB_URL` — не окремий сервіс, а те, що зафіксовано на #11: у dev
це `.env` поза git плюс файл-секрет, у prod — оточення й секрет-волюм
оркестратора; Infisical/Vault названі як наступний крок у «Куди це росте».
Значення вказує на базу цього репозиторію (`marketplace` на `127.0.0.1:5432`),
і жоден трекнутий env-файл, крім `.env.example`, його не містить:

```bash
for f in $(git ls-files | grep -E '\.env($|\.)' | grep -vE '\.example$'); do grep -lE '^(DATABASE_URL|DB_URL)=' "$f"; done   # порожньо
```

Числа беруться через `z.coerce.number()`, а не `z.number()`: усе, що приходить
з оточення, є рядком, і `z.number()` на `"3000"` впав би.

### Три файли й хто за що відповідає

| Файл | У git | Що в ньому |
| --- | --- | --- |
| `src/config/env.schema.ts` | так | джерело правди: перелік, типи, дефолти, `validate` |
| `.env.example` | так | контракт: усі змінні з коментарями, значення фейкові |
| `.env` | **ні** (`.gitignore`) | реальні значення цієї машини |
| `secrets/db_password` | **ні** (`.gitignore`) | пароль БД, який ротується |
| `secrets/pg_admin_password` | **ні** (`.gitignore`) | пароль адміністратора Postgres; генерує `db-up.sh` |

`npm run check:env` звіряє `.env.example` зі схемою і падає з `exit 1`, якщо
файл відстав: змінна є в схемі, але не у файлі — помилка; є у файлі, але не в
схемі — теж помилка; є, але без коментаря — теж. Правило конвенції: **додав
змінну в схему → додай у `.env.example` у тому ж коміті.**

### Запуск

```bash
pnpm install                 # або npm install
cp .env.example .env         # реальні значення цієї машини

npm run db:up                # Postgres у compose + файл-секрет зі стартовим паролем
npm run start                # білд + node dist/main.js → http://localhost:3000/v1
npm run start:dev            # без білду, через ts-node

curl -s localhost:3000/health      # процес живий, uptime
curl -s localhost:3000/health/db   # запит через пул до Postgres
```

`start` — навмисно НЕ watch-режим: watch не завершується і не віддає код
виходу, а весь сенс fail-fast саме в коді виходу. Watch живе окремо, у
`start:dev`.

Перевірити fail-fast можна за десять секунд:

```bash
mv .env /tmp && env -u DB_URL npm run start; echo "exit=$?"; mv /tmp/.env .
```

Процес не стартує, у виводі названа змінна `DB_URL` і причина, код виходу — не
нуль. `validate` у `ConfigModule.forRoot` виконується **до** створення DI-графа:
жоден провайдер не сконструювався, порт не відкрився, пул до БД не створився.

### Ротація пароля БД без рестарту

**Навіщо.** Пароль до БД треба міняти регулярно — за розкладом чи після
звільнення людини, яка його бачила. Якщо пароль приїхав у `process.env`, ця
зміна коштує рестарту всіх інстансів: оточення читається один раз при старті
процесу і після цього **замерзає**. Немає механізму, яким змінна оточення
живого процесу оновиться ззовні. Тому «змінити секрет» перетворюється на
«викотити реліз», і команди починають ротувати паролі раз на рік замість раз на
місяць.

**Як це обходиться.** Секрет — файл, а не змінна, і в `pg.Pool` поле `password`
задане **функцією**. Драйвер викликає її на кожне нове з'єднання
(`src/db/database.service.ts`), тож нове з'єднання читає файл заново. Postgres
перевіряє пароль лише під час handshake — уже відкриті з'єднання ротації не
помічають узагалі. Так само секрети монтують Docker Swarm (`/run/secrets/*`) і
Kubernetes (Secret як volume).

**Покроково:**

```bash
# 1. Підняти БД і застосунок (у двох терміналах)
npm run db:up
npm run start

# 2. Запам'ятати uptime
curl -s localhost:3000/health
# {"status":"ok","uptime_sec":42.317}

# 3. Ротація
npm run rotate      # або: bash rotate.sh

# 4. Запит, що ходить у БД, і той самий uptime-лічильник
curl -s localhost:3000/health/db
# {"status":"ok","db_user":"app_user","db_now":"...","uptime_sec":51.884}
```

`uptime_sec` більший за попередній — процес не перезапускався.

Що робить `rotate.sh` і чому саме в такому порядку:

1. `ALTER ROLE app_user WITH PASSWORD …` — нове значення стає істиною в БД;
2. **одразу** перезапис `secrets/db_password` — щоб нові з'єднання йшли вже з новим;
3. `pg_terminate_backend` по всіх з'єднаннях ролі — щоб наступний запит довів,
   що механізм працює, а не просто перевикористав старе з'єднання.

Між 1 і 2 є вікно у мілісекунди, коли нове з'єднання зі старим паролем впаде. У
продакшн-менеджерах (AWS Secrets Manager rotation, Vault database engine) це
лікують двома користувачами, що чергуються: поки живе `user_a` — ротують
`user_b`, і вікна немає зовсім.

Дві речі, на яких це ламається, і обидві не є багом ротації:

- **`pool.on('error', …)`** обов'язковий. Після `pg_terminate_backend` пул
  емітить `error` на об'єкті, якого ніхто не чекає, і Node падає з
  `Unhandled 'error' event`. Обробник є у `DatabaseService`.
- **`docker compose down -v`** знищує том, Postgres переініціалізується з
  `db/init.sql` і роль повертається до стартового пароля — а файл-секрет
  лишається з ротованим. Тому `scripts/db-up.sh` після підйому вирівнює пароль
  ролі зі вмістом файла.

### Секрети поза git і поза образом

У git не лежить ані `.env`, ані `secrets/` — обидва в `.gitignore`; контрактом
є лише `.env.example` з фейковими значеннями:

```bash
git check-ignore .env secrets/db_password   # обидва названі → ігноруються
git ls-files | grep '\.env'                 # лише .env.example
```

В образі — те саме, але канали витоку два, і `.dockerignore` закриває лише
один:

```bash
docker build -t marketplace-api .
docker run --rm marketplace-api ls -a /app        # є .env.example, немає .env і secrets/
docker inspect --format '{{.Config.Env}}' marketplace-api
docker history --no-trunc marketplace-api | grep -i password   # порожньо
```

Перший канал — файл із build-контексту, що заїхав у шар; його ріже
`.dockerignore`. Другий — `ENV SECRET=…` у самому `Dockerfile`: він живе не у
файловій системі, а в **конфігу образу**, і `.dockerignore` до нього не має
жодного стосунку. Обидва читаються **без запуску контейнера** — досить прав на
`docker pull`. Саме тому в `Dockerfile` цього проєкту немає жодного `ENV`, а
конфіг приходить у рантаймі: `docker run -e`, `env_file:` у compose або
секрет-волюм від оркестратора.

У git не лежить жоден пароль, включно з адміністраторським. Postgres отримує
його файлом — `POSTGRES_PASSWORD_FILE: /run/secrets/pg_admin_password` через
compose `secrets:` — а сам файл генерує `scripts/db-up.sh` у гітігнорному
`secrets/`. Роль `app_user` у `db/init.sql` створюється взагалі без пароля
(логін неможливий), значення ставить той самий `db-up.sh` зі
`secrets/db_password` — тож «дефолтного пароля» не існує ані секунди, і немає
двох джерел, які могли б розійтись. `rotate.sh` пароль адміна не потребує:
`psql` через `docker compose exec` ходить unix-сокетом усередині контейнера.

### Куди це росте

Схема env — єдина точка, куди наступні ДЗ додають свої змінні: `#12–13` —
підключення й міграції, `#23` — Redis, `#24` — ключі JWT. Ротаційний патерн
повернеться на `#28` (K8s Secrets) і `#31` (AWS Secrets Manager + KMS).
Наступний крок драбинки, який тут навмисно не зроблений, — винести значення з
машини у сховище (Infisical, Vault): тоді `.env` зникає взагалі, а секрети
приїжджають у процес-нащадок зі сховища.

## 6. Дата-шар

Схема, seed на реальний обсяг, чотири повільні запити API й індекси рівно під
них — усе в `db/`. Головна таблиця — **`orders`**, таблиця пошуку — **`products`**.

| Файл | Що робить |
| --- | --- |
| `db/schema.sql` | 7 таблиць, 10 FK, `CHECK`-и, генерована `tsvector`-колонка; жодного індексу, крім PK/UNIQUE, і жодного `DROP` |
| `db/reset.sql` | **єдиний файл, що знищує дані**: `DROP` усіх семи таблиць перед повторним прогоном схеми |
| `db/seed.sql` | 50 000 users · 120 000 products українською · 12 040 promotions · 200 000 orders · ≈385 000 order_items · ≈180 000 payments · ≈179 000 points_entries, перекошені розподіли, `VACUUM (ANALYZE)` наприкінці |
| `db/queries/q1..q4.sql` | замовлення покупця за період · черга `pending` · логін по `lower(email)` · повнотекстовий пошук по каталогу |
| `db/indexes.sql` | 4 індекси, по одному на запит: складений, partial, expression, GIN |
| `db/OPTIMIZATIONS.md` | 4 пари `EXPLAIN (ANALYZE, BUFFERS)` до/після, ціна tsvector, секція «Морфологія» |
| `scripts/db-bench.sh` | весь цикл нижче однією командою на чистому томі (`npm run db:bench`) |

Підняти базу: `npm run db:up`
Підключитись: `docker compose exec -T -w / db psql -U admin -d marketplace`

`psql` ходить unix-сокетом усередині контейнера, пароля не питає, а тека `db/`
змонтована в контейнер як `/db`, тому шляхи з репозиторію працюють як є.
Повний цикл руками, у тому ж порядку, що й перевірка:

```bash
psql() { docker compose exec -T -w / db psql -U admin -d marketplace -v ON_ERROR_STOP=1 "$@"; }

psql -f db/reset.sql                                             # ТІЛЬКИ для повторного прогону
psql -f db/schema.sql
psql -f db/seed.sql                                              # ~30 с
psql -c "EXPLAIN (ANALYZE, BUFFERS) $(cat db/queries/q1.sql)"    # до: Seq Scan
psql -f db/indexes.sql && psql -c "ANALYZE;"
psql -c "EXPLAIN (ANALYZE, BUFFERS) $(cat db/queries/q1.sql)"    # після: Index Scan Backward using idx_orders_buyer_created
```

Те саме для `q2`…`q4`; `q4` після індексу прогнати двічі-тричі, перший раз GIN
холодний. Чого тут навмисно немає: індексів «про запас» (кожен зайвий — диск і
повільніший `INSERT`, а `pg_stat_user_indexes` показав би його з `idx_scan = 0`)
і індексів у `schema.sql` (тоді не було б плану «до»). Пошук знаходить точну
словоформу: чому так і що з цим робити — «Морфологія» в `db/OPTIMIZATIONS.md`.

`schema.sql` не має жодного `DROP` навмисно: на заповненій базі він мусить
впасти на «relation already exists», а не мовчки знести дані. Перезалити —
рівно одна явна команда, `db/reset.sql`. На чистому томі (`npm run db:bench`,
`docker compose down -v`) вона не потрібна взагалі.

Акції, платежі й бали планам q1–q4 не потрібні, але в сіді вони є: інакше три
з десяти `FOREIGN KEY` — `orders.promo_code_id`, `order_items.promotion_id` і
пара на `payments`/`points_entries` — лишились би оголошеними, але жодного разу
не перевіреними під обсягом. Промокоди роздані так, щоб пара
(покупець, код) не повторювалась: частковий унікальний індекс із
`docs/design-notes.md` можна буде створити на #14 без чистки даних.

## Запуск

Повний перелік команд, змінних і кроків ротації — у розділі
[5. Configuration](#5-configuration). Найкоротший шлях:

```bash
pnpm install               # або npm install
cp .env.example .env
npm run db:up              # Postgres у compose + файл-секрет
npm run db:bench           # чистий том → schema → seed → EXPLAIN до/після (розділ 6)
npm run start              # http://localhost:3000/v1

npm run check:env          # .env.example звірений зі схемою
npm run lint:spec          # redocly lint openapi/openapi.yaml
```

Конфігурація pnpm — у `pnpm-workspace.yaml` (карантин на свіжі версії, контроль
install-скриптів, точний пінінг). `packageManager` свідомо не зафіксований, тож
працює з будь-яким менеджером; версії в `dependencies` запінені точно.
