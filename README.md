# mini-nest — IoC-контейнер + HTTP-шар на декораторах

Власний мікрофреймворк: контейнер читає типи параметрів конструктора з метаданих
і сам збирає граф залежностей, а маршрутизація й валідація живуть на декораторах
поверх голого `node:http`. Те саме, що NestJS робить під капотом.

ДЗ #6 і #7 курсу Node.js PRO.
Частина 1 — контейнер, частина 2 — request flow, попереду частина 3:
pipes / guards / interceptors (Л#8).

```bash
npm start          # http://localhost:3000
curl localhost:3000/users/42
curl "localhost:3000/users?limit=5"
curl -X POST localhost:3000/users -H 'content-type: application/json' \
     -d '{"name":"Ada","email":"ada@example.com","age":36}'
```

## Як запустити

Потрібен Node ≥ 22 (локально перевірено на v24.14.1), TypeScript 6.x.

```bash
npm ci        # або npm install при першій установці
npm test      # tsc → dist, потім node --test по dist/test/**/*.test.js
npm run build # тільки компіляція
npm run typecheck # перевірка типів без запису на диск
```

### У Docker

Образ той самий, що в ДЗ #5, за винятком однієї свідомої зміни: тут одна стадія
замість двох (пояснення — у коментарі всередині `Dockerfile`).

```bash
docker compose build
docker compose run --rm api npm test
```

`docker-compose.override.yml` монтує `./src` і `./test`, тож правки з хоста видно
без перезбірки образу. У CI цього файлу немає — там працює лише базовий
`docker-compose.yml`.

## Як це працює

Коли TypeScript компілює клас, **типи зникають** — у JS немає ані інтерфейсів, ані
анотацій параметрів. Контейнер, який хоче створити `new UserService(...)`, у
рантаймі не має звідки дізнатися, що першим аргументом треба підставити `Logger`.

Рівно цю дірку затикає прапорець **`emitDecoratorMetadata`**. Увімкнений, він
змушує компілятор дописати у вихідний JS виклик
`Reflect.metadata('design:paramtypes', [Logger, Config])` — масив **реальних
конструкторів**, а не рядків із назвами. Далі `reflect-metadata` (поліфіл сховища)
дає прочитати цей масив назад через
`Reflect.getMetadata('design:paramtypes', UserService)`, і контейнеру лишається
рекурсивно зарезолвити кожен елемент.

Дві умови, без яких масиву не буде, і обидві неочевидні:

1. **На класі має висіти хоч один декоратор.** Компілятор емітить метадані не для
   всіх класів підряд, а тільки для декорованих — інакше кожен клас у проєкті тягнув
   би за собою посилання на свої типи. Клас без `@Injectable()` не отримає
   `design:paramtypes` навіть при увімкненому прапорці. Саме тому `@Injectable()` —
   це не «оптимізація», без нього DI не працює фізично.
2. **Компілятор має вміти це емітити.** `emitDecoratorMetadata` — це *type-directed
   emit*: щоб записати в метадані конструктор `Logger`, компілятор мусить знати, що
   `Logger` — клас, а не інтерфейс. Це вимагає повного type-checker'а, який
   **esbuild свідомо викидає** заради швидкості. Тому `tsx` (esbuild) поверне
   `undefined` мовчки, при цілком коректному коді. Працюють `tsc`, `ts-node` і SWC
   з увімкненим `decoratorMetadata`. Node'ів `--experimental-strip-types` теж не
   годиться: він типи стирає, а не трансформує.

Побічний наслідок стирання типів: **інтерфейс у метаданих стає `Object`**. Резолвити
за таким «типом» нема чого — звідси `@Inject(token)` з явним `Symbol`. Клас придатний
як власний ключ `Map`, бо на нього є посилання; в інтерфейса посилатися нема на що.

## `forwardRef` — навіщо

Взаємний цикл `A ↔ B`, записаний звичайними типами, **не завантажується**:
компілятор емітить `design:paramtypes` одразу за оголошенням `A`, коли `B` ще
в TDZ, і процес падає з `ReferenceError: Cannot access 'B' before initialization`
ще до першого `resolve`.

```ts
@Injectable() class A { constructor(@Inject(forwardRef(() => B)) b: IB) {} }
@Injectable() class B { constructor(a: A) {} }   // A вже оголошено — можна за типом
```

Тунк відкладає обчислення токена до резолву, коли обидва класи вже існують.
Це не «дозвіл на циклічні залежності» — контейнер усе одно падає, але з
`CircularDependencyError: Circular dependency detected: A -> B -> A`
замість `RangeError` чи краху на завантаженні модуля.

## Реєстрація провайдерів

```ts
container.register(CONFIG, { url: '...' });        // useValue — готове значення
container.registerClass(USER_REPO, PgUserRepo);    // useClass — контейнер створить сам
```

`registerClass` потрібен там, де споживач залежить від інтерфейсу, а реалізацію
обирають зовні: сервіс пише `@Inject(USER_REPO)` і не змінюється, а складання
застосунку підставляє `PgUserRepo`, тест — фейк. Токен працює як аліас: скоуп
і залежності беруться з `@Injectable()` на класі, тож `resolve(USER_REPO)` і
`resolve(PgUserRepo)` віддають один і той самий синглтон. `useValue` має
пріоритет над `useClass` для того самого токена.


## Як параметр-декоратор знає, куди підставити значення

Коротка відповідь: **він не знає і не дізнається** — він лише лишає записку,
а підставляє значення диспетчер.

Це найконтрінтуїтивніше місце всієї конструкції. Пишеш `@Param('id') id: string`
і мимоволі читаєш це як «дістань `id` зі шляху». Насправді в момент, коли
декоратор виконується, **запиту ще не існує**: модуль щойно завантажився, сервер
навіть не слухає порт. Дістати нема звідки.

Тому декоратор робить єдине, що взагалі може, — пише в метадані методу рядок
розрідженої мапи:

```ts
// @Param('id') на нульовому аргументі методу findOne
Reflect.defineMetadata(PARAMS, { 0: { source: 'param', name: 'id' } },
                       UsersController.prototype, 'findOne');
```

### Чому саме індекс

Індекс параметра — **єдиний ключ, який переживає компіляцію**. Імена аргументів
у метадані не потрапляють взагалі, а типи не рятують: у
`findOne(@Param('id') id: string, @Query('q') q: string)` обидва аргументи мають
однаковий `design:paramtypes` — `String`. Розрізнити їх можна лише за позицією.
Це рівно той самий прийом, що в `@Inject` із частини 1: там мапа лежала на класі
(бо декорували конструктор), тут — на методі.

### Що робить диспетчер

На кожен запит він читає цю мапу і будує масив аргументів:

```
GET /users/42?limit=5
  → matchRoute      → { route: '/users/:id', params: { id: '42' } }
  → PARAMS мапа     → { 0: { source: 'param', name: 'id' } }
  → args[0] = params['id'] = '42'
  → handler.apply(controller, ['42'])
```

Одна деталь, на якій легко зловити баг: ітерувати треба **по індексах від 0 до
арності**, а не по ключах мапи. Мапа розріджена — аргумент без декоратора в ній
відсутній. Побудуєш список із `Object.keys(params)` — і такий аргумент просто
зникне, а всі наступні з'їдуть на позицію вліво.

### Порядок виконання декораторів

Знизу вгору й зсередини назовні: **параметр-декоратори → декоратор методу →
декоратор класу**. У межах одного списку параметрів — від останнього до першого
(`n-1 → 0`). Тобто на момент, коли спрацює `@Get(':id')`, мапа параметрів на
методі вже лежить, а коли спрацює `@Controller('users')` — уже лежать усі
маршрути. Ми на цей порядок не спираємось (кожен декоратор пише свій ключ
незалежно), але перевірено тестом `collectRoutes` — він бачить усе.

## Валідація: два кроки, які легко сплутати в один

`ValidationPipe` робить дві різні речі, і порядок принциповий:

1. **`plainToInstance`** — робить із plain-об'єкта екземпляр класу DTO.
   Без цього кроку `validate()` мовчки поверне порожній масив: правила лежать
   у `MetadataStorage` під конструктором, а в plain-об'єкта конструктор — `Object`.
   Тобто пропустило б будь-яке сміття, і без жодної помилки.
   Цей же крок дає `dto instanceof CreateUserDto` у хендлері.
2. **`validate` з `whitelist: true`** — перевіряє правила і вирізає поля, яких
   у DTO немає. Ріже саме на **вході**: без цього чужий `{"role":"admin"}`
   доїхав би до сервісу і далі в базу.

Чого тут свідомо немає — **приведення типів**. `{"age":"30"}` дасть 400
`age must be an integer number`: рядок так рядком і лишиться. Коерсія в
`class-transformer` вмикається окремим прапорцем `enableImplicitConversion`, і
не вмикати її — свідомий вибір, бо мовчазне приведення на вході дозволяє
протягнути «майже число» туди, де чекають число.

Помилка віддається **списком усіх полів**, а не першим:

```json
{ "statusCode": 400, "message": "Validation failed",
  "errors": [{ "field": "email", "constraints": ["email must be an email"] }] }
```

## `getMetadata` vs `getOwnMetadata` — правило в один рядок

**Читаєш — `getMetadata`, мутуєш — `getOwnMetadata`.**

`getMetadata` піднімається ланцюгом прототипів. У роутері це саме те, що треба:
контролер-нащадок успадковує маршрути базового класу (є тест). У декораторах
навпаки — вони мапу **дописують**, а `getMetadata` віддав би батьківський об'єкт
**за посиланням**, і `map[i] = …` дописав би чужий токен у батьківський клас.

## Ланцюг стадій замість лінійного коду

Обробка запиту — не список кроків, а **композиція**, той самий контракт, що в
Redux middleware і koa:

```ts
type Stage = (ctx: ExecutionContext, next: () => Promise<void>) => Promise<void>;

compose([bodyStage, argsStage, handlerStage]);
```

Навіщо, якщо кроків усього три і вони йдуть підряд. Тому що `(ctx, next)` дає
стадії **два** моменти — до `next()` і після:

```
a:before → b:before → b:after → a:after
```

Плоский список кроків дає лише перший. Interceptor з Лекції 8, який має
заміряти час навколо хендлера або підмінити відповідь, у плоскому списку
довелося б різати на дві окремі стадії й самому стежити, щоб вони не
розʼїхались. А guard — це просто стадія, яка **не викликає** `next()`: хвіст
ланцюга тоді не виконується взагалі.

`compose` стереже подвійний `next()`. Без цієї перевірки стадія, що випадково
викликала його двічі, тихо виконала б увесь хвіст повторно — хендлер
відпрацював би два рази на один запит, і в базі зʼявився б дубль.

## Пастка: `emitDecoratorMetadata` читає анотацію, а не виведений тип

Це коштувало окремого дебагу, тож окремим розділом:

```ts
list(@Query('limit') limit = 10)          // design:paramtypes → [Object]  ❌
list(@Query('limit') limit: number = 10)  // design:paramtypes → [Number]  ✅
```

Для type-checker'а обидва — `number`. Але метадані емітяться з **синтаксичної
анотації**, і без неї пайп не бачить, до чого приводити: `?limit=5` тихо
лишається рядком `'5'`. Ніякої помилки, просто інший тип у хендлері. Перевірено
тестом «emitDecoratorMetadata читає анотацію, а не виведений тип».

## Приведення типів на межі, а не в хендлері

У URL типів не буває: і `?limit=5`, і `/users/42` — рядки. Пайп приведення
дивиться в `design:paramtypes` хендлера і робить із них те, що оголошено:

```
GET /users?limit=5     → limit === 5      (number)
GET /users?limit=abc   → 400 «Query-параметр 'limit' має бути числом»
GET /users             → limit === 10     (дефолт із сигнатури)
```

`Number()`, а не `parseInt()`: `parseInt('12abc')` мовчки дає `12`, і опечатка
в query перетворюється на валідне, але не те число.

Це те, що в Nest роблять `ParseIntPipe` / `ParseBoolPipe`. Сенс — щоб
`NaN` не поїхав у сервіс і не вибухнув через три виклики звідси.

## Помилка клієнта не має виглядати як наша

`decodeURIComponent('%zz')` кидає `URIError`. Без `try/catch` у матчингу
`curl /users/%zz` давав **500** зі стектрейсом у логах — тобто чуже сміття
рахувалось нашою поломкою і забруднювало моніторинг.

Межу проводить `HttpError`: усе, що від нього успадковане, знає свій статус і
своє тіло відповіді, і диспетчер віддає його як є. Усе інше — 500 з логом і
без подробиць назовні (у текстах помилок бувають шляхи, SQL і імена таблиць).

## Обмеження

`@nestjs/*`, `inversify`, `tsyringe`, `typedi` не використовуються — контейнер свій.
